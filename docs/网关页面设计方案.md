### 1.2 核心问题：算了不用

`index.tsx` 中有 6 处**只定义、从未渲染**的状态——每个都只出现 1 次（定义处），全文件零引用：

| 变量 | 定义位置 | 内容 | 后果 |
|---|---|---|---|
| `actionSummary` | :170 | 运行态摘要（含 isDirty/hasRuntimeChanges） | 用户无法知道「改了但未生效」 |
| `integrationSummary` | :178 | endpointLabel / authLabel / logDirState / errorDigest | 接入四元组算了没用 |
| `latestErrorEntry` | :200 | 最近一条错误 | 有错误但界面不显示 |
| `lastStatusSyncAt` | :100 | 最近一次状态同步时间 | 无法判断数据新鲜度 |
| `copySuccess` | :93 | 复制成功提示 | `setCopySuccess` 被调用但无人显示 |
| `ThemedAlert` | :72 | 主题化警告条组件 | 整体未被使用 |

这不是「少写几个组件」，而是**已经算出来的信息被丢弃**。新增界面时应该优先复用这些，而不是重算。

### 1.3 配置区的问题：四个 Section 平铺

`GatewayConfig.tsx` 四个 Section 无分组、无折叠、无优先级：

```
Section 1: 网络与路由      ← 端口、region、账号模式、账号池、策略
Section 2: 客户端认证与模型 ← key 数、模型映射数、客户端配置
Section 3: 提示词过滤      ← 3 个开关 + 自定义规则
Section 4: 安全与高级      ← localOnly、自动启动、响应缓存、TTL
```

问题：
- **账号池选择器占满 Section 1**（`GatewayConfig.tsx:228-300`，含搜索/筛选/全选），把「端口」这种一行输入挤到角落
- 四个 Section 视觉权重相同，但使用频率相差一个量级
- 首屏没有「网关在干什么」的概览

## 二、设计目标

按用户的**任务**而非**配置项**组织。四种任务，按频率排序：

| 任务 | 频率 | 当前 |
|---|---|---|
| **T1 看状态**：在跑吗？出问题了吗？ | 每次打开 | 部分（缺错误、缺新鲜度） |
| **T2 接入工具**：把 Claude Code 接上 | 首次 + 换工具时 | 藏在弹窗 |
| **T3 排障**：为什么报错？ | 出问题时 | 日志弹窗（独立） |
| **T4 调优**：账号池、缓存、过滤 | 低频 | 首屏平铺 ❌ |

## 四、分区详细设计

### ① 运行状态区

**当前问题**：`consoleHighlights`（`index.tsx:203-227`）只有 3 张卡（Base URL / 密钥状态 / 路由模式），且密钥卡显示的是状态串。

**改为 4 张指标卡 + 一行同步信息：**

| 卡 | 数据来源 | 已有？ |
|---|---|---|
| 监听地址 | `effectiveBaseUrl` | ✅ consoleHighlights |
| 账号池 | `accounts.length` + 模式 | ✅ accounts |
| 客户端 Key | `countEffectiveClientApiKeys` | ✅ 本会话新增 |
| **错误** | 错误数 / 命中次数 | ❌ 需接 `integrationSummary.errorDigest` |

卡片下方一行：`最近同步 {{lastStatusSyncAt}}` —— 直接用已有 state 渲染，零新增逻辑。

**关键取舍**：错误卡点击展开 `RequestLogsDialog`（已有），无需新页面。

### ② 接入引导区（本方案的核心）

**为什么值得单列**：这是用户**唯一必须完成**才能用起来的事，而现在藏在 `快速配置客户端` 按钮后面。新用户要先点进弹窗才知道该做什么。

**布局：三列卡片，按客户端类型分**

```
┌────────────────┐ ┌────────────────┐ ┌────────────────┐
│ Claude Code    │ │ Codex CLI      │ │ 其他客户端      │
│ [Anthropic]    │ │ [Responses]    │ │ [Chat/通用]    │
│                │ │                │ │                │
│ Base URL       │ │ Base URL       │ │ Base URL       │
│ http://127...  │ │ http://127../v1│ │ http://127...  │
│                │ │                │ │                │
│ Header         │ │ Header         │ │ Header         │
│ x-api-key      │ │ Authorization  │ │ Authorization  │
│                │ │ Bearer         │ │ Bearer         │
│                │ │                │ │                │
│ [一键写入]      │ │ [一键写入]      │ │ [复制全部]      │
└────────────────┘ └────────────────┘ └────────────────┘
```

三张卡片的差异是**真实的**，不是装饰：

| 项 | Claude Code | Codex CLI | 其他 |
|---|---|---|---|
| Base URL | `{origin}` | `{origin}/v1` | `{origin}/v1` |
| 鉴权头 | `x-api-key` | `Authorization: Bearer` | `Authorization: Bearer` |
| 端点 | `/v1/messages` | `/v1/responses` | `/v1/chat/completions` |
| 写入路径 | `~/.claude/settings.json` | `~/.codex/auth.json` + `config.toml` | 手动 |

依据均在代码里：
- URL 差异：`gateway_cmd.rs:117` 的 `format!("{}/v1", proxy_origin)`
- 头兼容：`gateway/proxy/auth.rs:60-79` 的 `verify_client_auth` 同时认 `x-api-key` 与 `Authorization: Bearer`

**必须标鉴权头**：这是唯一无法从 URL 推断、且填错必 401（报错只说「客户端 API Key 无效」）的信息。

**空状态**（无生效 key 时）：
```
⚠ 尚未配置客户端密钥 —— 网关能启动，但所有客户端请求都会 401
   [生成密钥]
```
注：`createGatewayFieldErrors`（`gatewayPageUtils.ts:208`）已强制至少一个 key，所以此状态只在「全部 key 被禁用」时出现——`countEffectiveClientApiKeys` 可精确识别这种情况。

### ③ 高级配置（折叠）

把四个 Section 收进可折叠分组，按使用频率排序、默认收起：

| 分组 | 含 | 默认 |
|---|---|---|
| 网络与端口 | host / port / region / localOnly | 收起 |
| 账号池与路由 | accountMode / 池选择 / strategy / threshold | 收起 |
| 模型映射 | 入口按钮 + 规则数 | 收起 |
| 提示词过滤 | 3 开关 + 规则入口 | 收起 |
| 缓存 | responseCacheEnabled / TTL | 收起 |
| 安全 | 自动启动 / 允许 IP | 收起 |

**账号池选择器应移入独立弹窗** —— 它现在占 `GatewayConfig.tsx:228-300` 近 70 行，含搜索、状态筛选、全选，把同 Section 的「端口」输入框挤到边缘。配置区只需一行摘要 + 「配置账号池」按钮（该按钮已存在，见 `GatewayConfig.tsx:242`）。

## 五、必须处理的边界状态

设计不考虑边界就是没设计完。以下是**代码里已存在但界面未表达**的状态：

| 状态 | 触发 | 界面应表达 | 数据来源 |
|---|---|---|---|
| 改了未生效 | `hasUnsavedChanges` 但自动保存失败 | 状态区提示「配置未保存」 | `actionSummary` |
| 运行态与配置不一致 | `hasRuntimeChanges`（改了但未重启） | 提示「需重启生效」 | `actionSummary` |
| 网关未启动 + 有错 | 启动失败 | 显示 `latestErrorEntry` | 已有 state |
| 全部 key 被禁用 | `enabledCount === 0` | 接入区显式警告 | 本会话新增函数 |
| 账号池为空 | `accounts.length === 0` 且模式为 pool | 路由卡提示「无可用账号」 | `accounts` |
| 配置校验失败 | `hasFieldErrors` | 启动按钮已禁用 + 显示首条错误 | ✅ 已有 |
| 日志目录未定位 | `logDir` 为空 | 日志入口旁提示 | `integrationSummary.logDirState` |

`actionSummary` 与 `integrationSummary` 的存在说明**这些状态本来就要显示**，只是渲染被漏掉了。

## 六、落地顺序

| 步 | 内容 | 依赖 | 风险 |
|---|---|---|---|
| 1 | 渲染已有 state：错误卡、同步时间、`actionSummary` 状态提示 | 无 | 低（纯显示） |
| 2 | 抽 `buildGatewayClientRecipes()`：算出三张卡片的完整数据 | 无 | 低（纯函数 + 测试） |
| 3 | 接入引导区 UI（三卡 + 空状态） | 2 | 中 |
| 4 | 配置区折叠 + 账号池移入弹窗 | 无 | 中（结构调整） |
| 5 | 清理被取代的 `consoleHighlights` 卡片 | 3 | 低 |

第 2 步是关键：把「每个客户端该填什么」收敛成一个纯函数，卡片只是渲染。这样 URL / 头 / 路径的差异只有一处定义，不会像这次 API key 那样散落六处各写各的。

## 七、不做的事（明确排除）

| 项 | 原因 |
|---|---|
| 重做视觉风格 | 与现有设计语言一致即可，这不是视觉问题 |
| 实时图表 / 流量曲线 | `LogStore` 只存最近 10000 条，无时序聚合，成本远超收益 |
| 配置向导（多步 WIZARD） | 配置项之间有依赖但不多，折叠分组已足够 |
| 独立的「网关首页」路由 | 当前单页结构合理，问题在信息层级而非路由 |
| 移动端适配 | 桌面应用 |
