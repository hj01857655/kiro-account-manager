**G-1 具体后果**：客户端发 `thinking.type="disabled"` + `effort="xhigh"` 时，官方会降为 `high`（思考关着就不请求最深思考），网关原样下发 `output_config.effort="xhigh"`。上游未必报错，但与官方语义分歧，可能表现为「关了思考仍收得到 reasoning 事件」。

**G-2 具体后果**：若某模型 schema 的 `thinking.type.enum` 不含 `adaptive`（官方据此隐藏开关），网关仍会发 `adaptive`。触发条件=上游收紧该字段校验；表现=该模型请求 400。当前所有已实测模型都含 `adaptive`，所以是潜在风险而非现网缺陷。

另有一处**内部分歧值得注意**（不单列偏差）：降级分支可能判定某模型只支持 `enabled`（`payload.rs:254-257`），但 AMRF 信封仍发 `adaptive`（`:675`）——两条路径对同一语义用了不同判定依据（模型名 vs 硬编码）。因两侧只对「是否支持 AMRF」的模型集交集非空，实际影响面很小，但属于未来容易踩到的不一致。

### G-8（原优先级最高，已修→见 §3.1）

官方把截断原因显式编码后下发：`response.incomplete_details.reason` 经 `Ofd` 表映射成 `stopReason`——`max_output_tokens → MAX_TOKENS`、`content_filter → CONTENT_FILTERED`、`compaction_required_for_model_handoff → COMPACTION_REQUIRED_FOR_MODEL_HANDOFF`（第三键字面量已于 2026-10-22 静态还原，见协议面文档 §13），未知 reason 则**保持 `END_TURN`** 并上报 `createResponseUnknownIncompleteReason`。这条信息在原生路径同样以 `metadataEvent.stopReason` 存在。

网关完全没有消费它，于是「被 max_tokens 截断」和「被内容过滤拦截」都对外报成 `end_turn`。后果是**静默截断**：客户端（Claude Code / Codex / 官方 SDK）认为模型自然说完了，不会提示截断、也不会续写。

修的位置与形状（三处，缺一不可）：
1. `gateway/stream.rs` `AggregatedKiroResponse` 增加 `stop_reason: Option<String>`；`parse_kiro_event_full` 的 `metadataEvent` 分支（`stream.rs:96`）在提 `tokenUsage` 之外同时提 `stopReason`。
2. `gateway/proxy/responses.rs` `build_anthropic_response_with_stop`（`:157-176`）：上游给出 `MAX_TOKENS` 时输出 `stop_reason:"max_tokens"`，`CONTENT_FILTERED` 时输出 `refusal`（配合 G-9）。
3. `gateway/proxy/streaming.rs` 的 Anthropic 出站 `stop_reason`（`:1106`）同样优先取上游值，启发式只在缺失时兜底。

不新增重试、不新增字段透传链之外的分支；`stop_sequence` 命中仍优先（协议要求回填命中的序列）。

### G-8b：stopReason 枚举上界已取到，映射必须全量定策

已从 `extension.js` 还原出上游 stopReason 的**完整枚举**（内部常量 `ldi`，7 个值）：

```
END_TURN  MAX_TOKENS  TOOL_USE  CONTENT_FILTERED  PAUSE_TURN  MODEL_CONTEXT_WINDOW_EXCEEDED  UNKNOWN
```

逐个定下游行为（这是修 G-8 时必须一并定的，不能只处理 MAX_TOKENS）：

| 上游 stopReason | Anthropic 出站 | OpenAI Chat 出站 | Responses 出站 |
| --- | --- | --- | --- |
| `END_TURN` | `end_turn` | `stop` | `completed` |
| `MAX_TOKENS` | `max_tokens` | `length` | `incomplete` + `max_output_tokens` |
| `TOOL_USE` | `tool_use` | `tool_calls` | `completed`（带 function_call item） |
| `CONTENT_FILTERED` | `refusal`（+ 回填 `refusal` 字段，见 G-9） | `content_filter` | `incomplete` + `content_filter` |
| `PAUSE_TURN` | ✅ `pause_turn`（Anthropic 官方自有枚举，直接透传；原表写「无标准对应」已推翻，见 §3.2） | `stop`（OpenAI 无对应值，不发明） | `completed` |
| `MODEL_CONTEXT_WINDOW_EXCEEDED` | `max_tokens`（语义=输出被窗口截断，与截断可重试） | `length` | `incomplete` + `max_output_tokens` |
| `UNKNOWN` | `end_turn` | `stop` | `completed` |

两个判断约束：一，`PAUSE_TURN` 在官方 Kiro 语义里是「长回合待续」，映成 `end_turn` 会让客户端不自动续，这是**已知代价**，需真实流量确认频率后再调；二，`MODEL_CONTEXT_WINDOW_EXCEEDED` 与 `MAX_TOKENS` 在上游是两个值，不合并——前者是窗口配置问题（重试无用），后者是输出长度问题（客户端可提高 `max_tokens` 后重试），合并将误导客户端重试。

### G-14（新）：上游有两个错误码直接对应网关现有逻辑

枚举 `gs`（共 26 项，已全量还原）中这两项与网关行为直接相关：

- **`THINKING_SIGNATURE_INVALID`**：上游会校验回传的 thinking signature。网关目前把 `signature` 存在 `aggregated.thinking_signature` 并写入 Anthropic 出站 block（`models/anthropic.rs:73-75`），但 **OpenAI Chat 入站回传时没有 signature 通道** → 多轮下要么丢思考要么丢签名。修 G-7 时需一并验证该路径不会触发此 400。
- **`TOOL_USE_RESULT_MISMATCH`**：上游强校验 assistant 的 `toolUses` 与下一条 user 的 `toolResults` 匹配。网关已有 `order_tool_results_like_previous_tool_uses` 与 `payload.rs:27` 的 TOOL_USES_AND_RESULTS 校验注释，属**已覆盖**；但该枚举手明它会被拒收，不是静默丢弃——因此 G-8 修完后的回归测试要覆盖工具分支。

### 3.2 G-8b 修正：`pause_turn` / `refusal` 不是非标值

上一版定策时判断「Anthropic 只能直接表达 `end_turn`/`max_tokens`/`tool_use`」。核对官方协议文档
`docs/protocol/anthropic-messages-api.md` §5.2 后证实：**Anthropic `stop_reason` 本身就含
`refusal` 与 `pause_turn`**，且明确要求「实现应把停止原因作为可扩展字符串处理」。
因此实现里没有做降级：`CONTENT_FILTERED → refusal`、`PAUSE_TURN → pause_turn` 原值直通，
不会把「长回合待续」误报成正常结束。仅 `UNKNOWN` 回退 `end_turn`（上游自身也未定性，无更多信息可传）。

## 7. 官方工具协议 2026 更新（2026-10-23）

与前面 G-n 不同，这些不是「网关没做到」，而是「上游协议变了，网关需跟上」。

### 7.1 Anthropic `2026-10-21`（首个正式版本，三条 breaking change）

| 采样参数移除：请求带 `temperature` / `top_p` / `top_k` 一律 400（即使等于默认值） | `field_support.rs` 三个字段均 `Rejected`（`top_k` 原本已拒，本次补上另两个）。上游 Kiro 本就不消费这三个字段（`payload.rs` 零引用），拒绝前是静默丢弃 | ✅ 已对齐 |

### 7.2 工具按官方 Execution 列分类（关键修复）

官方 `tool-reference` 把工具分两类，**两类都带日期化 `type`**：

- **Server**（Anthropic 基础设施执行）：`web_search_*` / `web_fetch_*` / `code_execution_*` / `advisor_*` / `tool_search_tool_*` / `mcp_toolset`
- **Client**（客户端执行，schema 由 Anthropic 定义）：`memory_*` / `bash_*` / `text_editor_*` / `computer_toolset_*` / `browser_toolset_*`

原实现用 `type != "custom"` 一刀切当 server tool 剥离，**把 5 个 Client 工具也剥了**——模型看不到工具，客户端功能直接失效。

修复：`converter/tools.rs::is_server_executed_tool()` 按上表白名单判定（前缀 + 下划线边界），未知 `type` 保留而非剥离（官方会持续加新版本，剥错代价更大）。

### 7.3 Tool Search（`tool_search_tool_*_20251119`）

官方版本号仍是 `20251119`（最新模型 Fable 5.1 / Opus 5.5 均只支持该版），与 API 版本 `2026-10-21` 相互独立。

| 官方约束 | 网关实现 | 状态 |
| --- | --- | --- |
| regex 模式 ≤200 字符，BM25 query ≤500 字符 | `MAX_REGEX_PATTERN_LEN` / `MAX_BM25_QUERY_LEN`；长度只算 pattern 本体（`re:` 是网关自定前缀，不计入） | ✅ |
| `limit` 1..=10000，默认 5 | `MAX_LIMIT = 10_000`，`DEFAULT_MAX_RESULTS = 5` | ✅ |
| regex 变体入参名是 `pattern`，bm25 是 `query` | 合成工具 schema 两名都声明，`execute_tool_search` 两者都消费 | ✅ |
| 检索工具自身不可 `defer_loading`，至少保留一个非延迟工具 | `split_deferred_tools` 注入的合成工具不带 `defer_loading`；`tool_choice` 强制指定时不拆分 | ✅ |

| `tool_search_tool_result` / `tool_reference` 块类型 | 网关走客户端代答路线（`tool_result` + 完整定义文本），不依赖这两个块；客户端若按官方格式回传历史，`converter/content.rs` 不识别——**已知限制** | 🟡 |
| 流式代答 | `run_tool_search_buffered_loop`：缓冲整轮 EventStream、跑同构代答环、最后一轮原始字节重建交既有流式管线 | ✅ |

代答环的回合构造（`build_tool_search_turn`）为非流式/流式共用，已有单测锁定：只取第一个调用、`tool_use_id` 与 assistant `id` 一致、官方别名调用被拦截且历史保真。**真实流量的 SSE 时序仍需 defer_loading 客户端实测**。

### 7.4 Client toolset：不展开（有意偏差）

`computer_toolset_20260801` / `browser_toolset_20260801` 是「一个无名条目，声明一组固定成员」。官方明确：

```text
The computer use tool is implemented as a schema-less tool... the schema is built into
Claude's model and can't be modified.
```

因此网关**无法保真**：
1. 成员 schema 不对外提供（官方只给 markdown 表格，无机器可读定义），展开必须伪造；
2. 成员调用的 `toolset_name` 元数据由 Anthropic API 端渲染，展开后客户端按 `(toolset_name, name)` 分发依然失败。

当前策略：跳过并 warn（`normalize/anthropic.rs`），请求不报错，功能不可用。
